# SECURITY.md — REALSPACE Website Rebuild

Scope: a low-attack-surface marketing site with one sensitive area (the Admin Dashboard) and one data-collection surface (leads/quote calculator). Security posture is proportionate — not enterprise-grade over-engineering, but no shortcuts on the parts that matter: admin auth, lead PII, and file uploads.

## 1. Admin Authentication

- **Single admin role** for v1 (the client is a sole proprietor). No public self-registration — `AdminUser` rows are seeded manually/via a one-time script, never via a public signup form.
- Auth via Auth.js credentials provider: email + password, `passwordHash` stored with **bcrypt/argon2**, never plaintext or reversible encryption.
- Session via secure, `httpOnly`, `SameSite=Lax` cookies. No JWTs stored in `localStorage`.
- Every route under `/admin/**` and every admin Server Action/route handler re-checks the session server-side — the client-side redirect on an unauthenticated dashboard visit is a UX nicety, **not** the security control.
- Rate-limit the login endpoint (e.g., 5 attempts / 15 min per IP) to blunt credential-stuffing/brute force.
- No "remember me forever" — session expiry (e.g., 7 days) with re-auth required after.

```ts
// admin/layout.tsx — pattern, not literal final code
export default async function AdminLayout({ children }: { children: React.ReactNode }) {
  const session = await auth();
  if (!session?.user) redirect("/admin/login");
  return <>{children}</>;
}
```

Every admin Server Action independently calls `auth()` and checks the session again — layout-level guarding alone is not sufficient because Server Actions can in principle be invoked directly.

## 2. Authorization

- v1 has one role (`admin`), so authorization = authentication. The schema (`AdminUser`) is deliberately structured so a `role` field could be added later without a rewrite, but this is **not** built speculatively now (see CODING_STANDARDS.md — avoid premature abstraction).

## 3. Input Validation

- Every public-facing mutation (quote submission, contact form) and every admin mutation validates input server-side with a schema library (e.g. Zod) **before** it touches Prisma — never trust client-side validation alone.
- Numeric fields (carpet area, pricing values, quantities) are validated for sane ranges to prevent absurd/garbage data or overflow-style abuse of the calculator.
- Free-text fields (`description`, `requirements`, `notes`) are length-capped and stored as-is (Prisma parameterizes queries, so SQL injection is not a concern) — but are **HTML-escaped on render**, never rendered as raw HTML, to prevent stored XSS via lead submissions or testimonial content.
- `Lead.email`/`phone` format-validated but not treated as verified — no OTP requirement for v1 (would add friction to the primary conversion funnel).

## 4. File Upload Security (Cloudinary)

- The Next.js server never receives raw uploaded file bytes. The Admin browser uploads directly to Cloudinary using a **short-lived signed upload request** generated by `api/cloudinary/sign` (auth-guarded, admin-only).
- Signed uploads restrict: allowed folder, allowed formats (image/video only), max file size, and an expiring timestamp — configured server-side when the signature is generated, not trusted from client input.
- Cloudinary's own malware/format validation covers file-type spoofing; the app additionally restricts accepted `resource_type` to `image`/`video`.
- Public project images/videos are served from Cloudinary's CDN — the app stores only URLs and `public_id`s, never binary blobs, keeping the DB and serverless functions out of the file-serving path entirely.

## 5. Rate Limiting & Abuse Prevention

- Public POST endpoints (`api/quote`, `api/contact`, login) are rate-limited per IP (e.g., via Vercel Edge Middleware + a lightweight store, or an upstream provider) to prevent spam/lead-flooding and brute force.
- A honeypot field (hidden, bot-only) on the contact and quote forms to cheaply filter basic bots without adding CAPTCHA friction for real users; add CAPTCHA (e.g., hCaptcha) only if spam volume in production proves the honeypot insufficient — avoid pre-emptive friction on the primary conversion path.

## 6. Secrets & Environment Variables

- `DATABASE_URL`, Cloudinary API secret, Auth.js secret, and any signed-URL secrets live only in Vercel environment variables (per-environment: production/preview/development) — never committed to the repo, never logged.
- `.env.local` is gitignored; `.env.example` documents required variable names with placeholder values only.
- Cloudinary's **unsigned** upload preset is never used for admin uploads — signed uploads only, so an attacker cannot exfiltrate the ability to upload arbitrary media to the client's account by reading client-side JS.

## 7. Data Privacy (Lead PII)

- `Lead` rows contain name, phone, email, location, requirements — treat as PII: accessible only through authenticated admin routes, never exposed via any public API or included in client-side bundles/props.
- No third-party analytics/marketing pixel receives lead form field values — analytics (GA4) tracks conversion *events*, not the PII payload itself.
- Testimonials sourced from real clients (per brand report §8/§13) are published only with the client's name/locality as agreed — no full addresses or phone numbers ever rendered publicly.

## 8. Transport & Headers

- HTTPS enforced end-to-end via Vercel (automatic).
- Security headers set via Next.js `headers()` config or middleware: `Content-Security-Policy` (allow-listing Cloudinary + self), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (no reason for the site to be iframed).

## 9. Dependency & Supply Chain Hygiene

- Lockfile committed (`package-lock.json`/`pnpm-lock.yaml`); `npm audit`/Dependabot alerts monitored, especially given AI-agent-assisted development where dependencies may be added without full manual review (see CODING_STANDARDS.md §"AI agent constraints").
- No dependency is added by an AI coding agent without the addition being visible in a diff the developer reviews before commit.

## 10. Known Risk Accepted for v1 (documented, not hidden)

- No 2FA on the single admin account in v1 — proportionate to a single-user, non-financial-transaction system; revisit if the dashboard ever handles payments or multiple admin users.
- No formal WAF beyond Vercel's platform-level protections — acceptable for current traffic/threat profile; revisit if the site becomes a target (e.g., visible spike in credential-stuffing attempts on `/admin/login`).
